# Release `v0.4.3`

## Release

- version: `v0.4.3`
- date: `2026-08-02`

## Summary

One fix, prompted by a real operator hitting it.

- **a failed console unlock now explains itself.** Unlocking decrypts the
  gateway's secret store with the passphrase, so a wrong passphrase always
  fails inside AES-GCM — and the handler returned that library error verbatim:
  `Unsupported state or unable to authenticate data`. To an operator that reads
  like the gateway is broken, not like a wrong passphrase, and it sent someone
  looking for a bug in the verifier while the verifier was working correctly.
  The unlock endpoint no longer surfaces the decryption error at all.

- **pasting the deployment key into the passphrase box gets its own answer.**
  It is a predictable mix-up: both are long opaque strings, the reset link sits
  directly under the unlock field, and the deployment key is the one an
  operator can always retrieve from the host. That case now returns
  `AUTH_BOOTSTRAP_SECRET_IS_NOT_PASSPHRASE` and points at the reset flow, which
  is where the deployment key is actually used.

- bootstrap-secret comparison is now constant-time.

## Compatibility

Drop-in over `v0.4.2`. No environment or API changes. One new error code on
`POST /session/login`; existing clients treat it as any other 401.
